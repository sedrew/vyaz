# office-metrics — PowerPoint line-box calibration

Answers "what line height does PowerPoint actually use in `mode: 'office'`?"
Counterpart to `scripts/browser-metrics/` (which calibrates *width* vs Chrome).

## Files

| file | what |
|---|---|
| `gen-line-spacing.ts` | builds `line-spacing.pptx` — isolates the paragraph **line-spacing multiplier** (`<a:spcPct>` 1.0 / 1.5 / 2.0), separately and stacked. pptxgenjs, needs only `bun` + Roboto installed |
| `line-spacing.pptx` | generated; **5 slides, one plain TextBox each** (no groups, no marker rects). Open in PowerPoint, let it re-wrap, save, then per slide File ▸ Export ▸ SVG → `office-cases/<case>/powerpoint.svg` |
| `textframe-fit-run.ts` | **vyaz side** of the fixed-rectangle round-trip: feeds `(text, width)` to `layoutTextFrame(…, {mode:'office'})` for Roboto + Arial, records `content.height` (where the last line box ends) + the line breaks / baselines, writes `textframe-fit.json`. Input matrix (`WIDTHS_PT` / `VARIANTS`) at the top |
| `gen-textframe-fit.ts` | **PowerPoint side**: reads `textframe-fit.json`, builds a TextBox at **exactly** each `width_pt × height_pt` (wrap-only, no autofit element, insets 0) plus a `<name>@fit` twin (`<a:spAutoFit/>`, PowerPoint rewrites its `cy` on save) — the still-open "does autofit trim to `content` or `textBox`" question |
| `textframe-fit.json` | round-trip manifest: per frame `{ width_pt, height_pt (vyaz), font_size_pt, line_spacing, text, vyaz.lines[…] }` — matches each exported SVG back to the `layoutTextFrame` call |
| `gen-font-grid-diagnostic.ts` | one slide per font (Roboto / Arial / Unifont / Times New Roman), grid of 11 sizes (6–70pt) × 5 line-spacing multipliers (100–200%). Each cell: a shape sized to vyaz `textBox` (fit:'none', exact size) with underlined, highlighted text — open in PowerPoint, export, and the baseline should sit flush with the box bottom if the `OFFICE_BASELINE_RATIO` model is right for that font. This is what found `(typoAscFrac + winAscFrac) / 2` and the `useTypoMetrics` carve-out below |
| `font-grid-diagnostic.pptx` | generated by the above |
| `gen-wrap-diagnostic.ts` | does PowerPoint wrap text where vyaz does? Module: adds two slides (Roboto, Arial; cases in 2 columns, 3 boxes per case: natural / forced / fit-width) to `kern-context.pptx` |
| `gen-kern-context.ts` | `kern-context.pptx` — slide 1: where PowerPoint applies a kern pair (fit boxes, 3 fonts); slides 2–3: the wrap diagnostic above |
| `gen-glyph-alphabet.ts` | `glyph-alphabet.pptx` — every character its own run and background colour → per-glyph advances from the SVG export (Roboto vs Times New Roman) |
| `gen-stress.ts` | `stress.pptx` — 30 slides × 8×6: 12 fonts, 8 → 120pt, regular / bold / italic, every box sized to vyaz's office width exactly; a box that wraps in PowerPoint is a bug |
| `RESULTS.md` | the office line-box calibration outcome: the model, the constants, measured vyaz↔PowerPoint agreement, what is still open |

```bash
bun scripts/office-metrics/gen-line-spacing.ts          # regenerate line-spacing.pptx
bun scripts/office-metrics/textframe-fit-run.ts         # vyaz -> textframe-fit.json
bun scripts/office-metrics/gen-textframe-fit.ts         # textframe-fit.json -> textframe-fit.pptx
bun scripts/office-metrics/gen-font-grid-diagnostic.ts  # -> font-grid-diagnostic.pptx
bun scripts/office-metrics/gen-kern-context.ts          # -> kern-context.pptx (incl. the wrap diagnostic)
bun scripts/office-metrics/gen-glyph-alphabet.ts        # -> glyph-alphabet.pptx
bun scripts/office-metrics/gen-stress.ts                # -> stress.pptx
```

Every generator above only *writes* `.pptx` files — none of them drive PowerPoint. The PowerPoint side (open, save if testing autofit, File ▸ Export ▸ SVG) is manual; there's no reliable way to automate it from an agent/headless session (no WindowServer access), so don't try.

`line-spacing.pptx` is a **pure SVG-export** oracle. Its slides mirror the golden
corpus in `packages/renderers/tests/office-cases/line-spacing-*` one-to-one (same
text, 200 pt column, Roboto 18, line spacing 1.0 / 1.5 / 2.0) — slide order =
case order, don't swap `stacked` / `mixed`. In vyaz today `mode: 'office'`
ignores the multiplier, so 100/150/200 render at the same height; the export
says what PowerPoint actually does. See
`office-cases/MIGRATION.md` for the derived model and the diff.

## Findings (historical: measured on the hand-fitted `font-metrics.pptx` oracle deck and its `report.md`, both since removed)

- **This suggests the line box is `1.2 × fontSize`, font-independent.** Great
  Vibes (OS/2 win ratio ≈ 1.75) got the *same* ~1.2× box as Roboto, and a
  10-line wrapped stack landed on 1.201/line. No single fontkit table field
  (`win` / `hhea` / `typo` / `head`) yields ~1.2 for both fonts.
- **Not applied.** vyaz still uses `mode: 'office'` =
  `ascent/descent = winAscent/winDescent × 1.078` (fitted to Arial:
  `1.117 × 1.078 ≈ 1.2`), which matches the fonts we care about. Switching to a
  flat `1.2 × maxRunSizeInLine × lnSpc%` is an open question — see the roadmap
  ("Exploring"). It needs more oracle data (a display/script font with a large
  `hhea`) and a decision on `lnSpc%` handling before it's worth an `office`-mode
  behaviour break.
- **Width needs no calibration — but only with shaping on.** fontkit `layout()`
  (GPOS+GSUB) matches PowerPoint's selection box to ±0.4%; that was always
  measured with shaping requested explicitly, not vyaz's old default
  (plain advance-sum). `LayoutOptions.shaping` now defaults to `true` for
  `mode: 'office'` because of this — see RESULTS.md "`shaping` now defaults
  to `true` for `mode: 'office'`".

## ⚠ Environment

Measured on **macOS (PowerPoint for Mac)**. The `1.2` constant is undocumented
PowerPoint behaviour and may drift slightly by OS and PowerPoint build; the
spread in this deck was 1.20–1.215. To retarget (e.g. Windows-exact), re-run the
generators here and export their decks to SVG on that platform. Adding a display /
script font with a large `hhea` line height (Lobster, Pacifico, Alfa Slab One)
would also let the "flat 1.2" vs "max(1.2, hhea/upm)" models be told apart.
